案一

macOS arm64 · test_cov_lua_runtime f3d2a75 已修复 · CI 验证

1/90 用例崩溃;崩溃点在测试方法自身的栈帧里,而不在被测代码。

症状 · .ips 指纹
Exception Type: EXC_BAD_ACCESS (KERN_INVALID_ADDRESS) fault addr: 0x9 stack: luaH_getint ← lua_rawgeti ← luaL_unref ← test_method x10: absentkey ; ltable.c 的哨兵节点
根因

sol::state_view 并非纯视图——构造即持有 reg 与 global 两个 registry 引用,析构时各跑一次 luaL_unref。用例第 4 段 vm2.reset() 关闭 VM 后,sol::state_view lua2 仍存活到作用域收尾才析构,对已关闭状态执行 unref。平台差异:Linux glibc 释放后内存仍映射,悬垂读静默存活;macOS arm64 释放即不可访问,registry 指针读出 NULL,读 Table::lsizenode(偏移 9)恰好就是崩溃地址 0x9。

// state_view.hpp:110 —— 构造即取两个引用 state_view(lua_State* Ls) : L(Ls), reg(Ls, LUA_REGISTRYINDEX), global(Ls, global_tag) {}
修复

凡测试要在 VM 生命周期内关闭它:把所有引用该状态的 sol 对象——state_view、function、table、proxy 链——收进内层作用域先析构,再 reset VM;越界的只留 weak 句柄与 abandon() 过的 handler。

排障注

CI 是 Release/NDEBUG,sol2 安全宏与 Debug 不同——本地 Debug 树复现不了,须另建 Release 树;sol2 探针一度打错 vcpkg 包含路径(实际读取的是仓库根 vcpkg_installed/ 而非构建树内的),靠 .o.ddi.d 依赖文件定位真实包含路径后取证才生效。

案二

Linux · test_cov_lua_service fc3b4ea 已修复 · CI 验证

最小的一案,但同样属于"诊断路径自己成为崩溃源"的家族。

根因

pending_calls_inspect(挂起调用诊断接口)在 shared_lock 之外用裸指针 sort / 逐条读取,与并发的 pending_calls.erase 构成 use-after-free。

修复

整函数持 std::shared_lock,sort 与读指针全部移入锁内,与同文件 timer_inspect 的既有形态对齐。

案三

Windows · test_cov_lua_service 6e30d72 已修复 · CI 验证

本案主轮次:33 路并发压出的跨线程竞态,修复过程中还纠正了一版"看起来更安全"的半成品方案。

症状 · 日志指纹(节选)
CI: run 35676872571 · windows-latest Test step · exit 8 *** resume_diag: FAIL co=…1608 status=2 lstat=2 top=3 errtype=string … *** resume_diag: FAIL co=…C368 status=2 lstat=0 top=1 errtype=string … *** shield resume requeue: co=…C368 session=… retries=1 src=call-response Segmentation fault

触发用例 InspectCapsTruncated:33 路并发 call_timeout(9000) 打向同一 target,target 端 shield.sleep(600) 后同时响应,期间 inspect 轮询。两条 FAIL 分属两个协程,requeue 打印之后立即崩溃。

语义判定

lua_resume 返回 "cannot resume non-suspended coroutine" 当且仅当另一线程正持该协程帧。kernel 拒绝时会弹掉本次推送的参数、把这条消息压到协程栈顶——此后本线程对该协程的任何 lua_* 触碰都是跨线程竞态:读到的是驱动线程的活跃栈顶,MSVC 下直接崩,glibc 下静默幸存。

根因 · 同臂四处 UB
  1. lua_settop(co, 0) 清场(元凶)——把栈顶拽到栈底,驱动线程的 ci->func 相对寻址随即越界;日志里 requeue 打印后立即崩,位置吻合。
  2. 诊断打印跨线程读 lua_status / lua_gettop——被拒协程的栈正被别的线程驱动,读它本身就是数据竞争。
  3. service_actors 查找在锁外裸读 unordered_map。
  4. retry 耗尽时对可能仍被驱动的协程做终局拆除(luaL_unref + note_coroutine_finished)。
修复

清场语义保留,实现从无界拽栈换成有界弹槽——紧随被拒 resume 执行,弹掉的正是 kernel 刚压入栈顶的拒绝消息:

- lua_settop(caller_co, 0); // 清场:无界拽栈,Windows SegFault + lua_pop(caller_co, 1); // 有界弹槽:单槽指针递减,内存安全

之后的分类只读互斥锁保护的书:non-suspended → 锁内恢复挂起条目 + 经 caller actor 邮箱重投(retry 预算耗尽也只丢弃等待,绝不拆除);dead / 续体错误 → 协程确由本线程终结,原有的 settop / unref / note_coroutine_finished 拆除合法。

必要的清场 · 修复中的反复
第一版"只删 settop、完全不碰"同样错。YieldWindowDropWithoutCallerActor 随即转红 [0 != 42]:被拒时 kernel 压入的消息残留帧内,而测试续体用 lua_gettop 收全栈打 payload——消息把返回值整体顶错一位。结论:清场是必要语义,"弹 1 槽"不是可选项而是唯一既满足清场又内存安全的实现。
